Section 1: Agentic AI Fundamentals

1.1 What is an Agent? (Philosophy + Practical Definition)

Philosophical Definition:
An agent is a system that perceives its environment, reasons about it, and autonomously takes actions to achieve specific goals—without explicit human intervention at each step.
Practical Engineering Definition:
An agent is a loop that:
  • **Perceives** context, user intent, environment state, and previous results
  • **Reasons** using LLM to decide next action from available tools
  • **Acts** by executing selected tools and capturing results
  • **Reflects** on outcomes to decide: continue loop or exit?

💡 Key Insight: The Fundamental Difference

A **chatbot** waits for user input and responds. A **workflow** follows a predetermined sequence. An **agent** autonomously decides its next action based on reasoning.

1.2 Why Build Agents? (Real-World Use Cases)

🔬 Research & Analysis

Autonomous research agents that search web, analyze docs, synthesize findings without human guidance at each step

🛠️ Software Engineering

Code generation agents that understand requirements, plan implementation, write code, test, debug iteratively

📊 Data Analysis

Data agents that explore datasets, formulate hypotheses, run analyses, create visualizations autonomously

💼 Business Operations

Operational agents handling customer inquiries, resolving issues, escalating appropriately without manual triage

🧪 Scientific Discovery

Research agents designing experiments, analyzing results, formulating new hypotheses in scientific domains

1.3 Five Dimensions of Agent Design (Deep Analysis)

① Autonomy Level

Spectrum: Supervised → Gated → Autonomous

Supervised: Every action requires human approval before execution
  • User sees: "Agent suggests X, approve? Y/N"
  • Real example: Compliance-critical financial transactions
  • Cost: Every action = human latency (seconds to minutes)
Gated: Critical actions require approval, routine actions execute freely
  • User sees: Notifications only for significant decisions
  • Real example: Data operations (read approved, write/delete gated)
  • Cost: Medium (only critical actions blocked)
Autonomous: Agent executes all decisions, human reviews results
  • User sees: Final results + decision log
  • Real example: Research agents, code generation
  • Cost: Fast (no approval latency) but higher risk

② Tool Access & Sandboxing

Principle: Least privilege access for maximum safety
  • Read-Only: Access databases, APIs, documents for information only
  • Safe Mutations: Create, update non-critical data; delete forbidden
  • Full Access: Can create, update, delete anything
  • Sandboxed Execution: Code runs in isolated environment; can't access production

⚠️ Critical Design Pattern: Gradual Escalation

Don't grant full access to new agents. Start with read-only tools. After validation, grant safe mutations. Monitor extensively before full access. This prevents catastrophic failures from reasoning mistakes.

③ Error Recovery Strategy

Levels (ordered by resilience):
  • Fail-Fast: Error encountered → stop immediately, return error
  • Retry Logic: Transient error → retry 3x with exponential backoff
  • Fallback Tools: Tool A failed → try alternate Tool B
  • Human Escalation: Repeated failures → notify human, wait for input
  • Circuit Breaker: Tool fails repeatedly → disable temporarily, resume later

④ State & Memory Architecture

Three memory tiers in modern agents:
  • Context Window Memory: Current message history (4K to 200K tokens)
  • Long-Term Memory: Database storage (persistent, queryable)
  • Semantic Memory: Vector embeddings of key information (similarity search)
Critical Question: If agent crashes/restarts, is memory lost?
  • In-memory only → YES, lost (dangerous for production)
  • Database persisted → NO, recoverable
  • Hybrid → Depends on what you persist

⑤ Loop Termination Conditions

Production agents need multiple termination signals:
  • Goal Achievement: Agent declares "task complete" (LLM judgment)
  • Max Iterations: Safety limit (e.g., 10 loops max)
  • Token Budget: Cost control (e.g., $0.50 spent → stop)
  • Time Limit: Latency SLA (e.g., 60 seconds max)
  • Stuck Detection: Repeated tool calls → agent spinning wheels

⚠️ Common Production Failure: Infinite Loops

Many agents fail by entering infinite loops where the LLM keeps calling tools that return the same result. Always implement loop detection: track which tools were called, detect repetition, break the loop after N identical calls.

Section 2: Agent Anatomy & Building Blocks

2.1 The Agent Loop (Detailed Breakdown)

Phase ①: GATHER CONTEXT
↓ Collect user intent, conversation history, environment state, available tools

Phase ②: REASON & DECIDE
↓ LLM analyzes: what's the goal? What tools needed? In what order?

Phase ③: TAKE ACTION
↓ Execute selected tools, capture results, handle errors

Phase ④: OBSERVE & REFLECT
↓ Did action succeed? Is goal achieved? Should I continue?

↻ Loop back to Phase ① or EXIT

2.2 Tool Design Patterns

Tools are the agent's hands. Good tool design makes or breaks agents.

Tool Granularity: The Goldilocks Problem

Too Fine-Grained (Bad)
tools = [ get_db_connection(), # Agent must compose DB calls execute_query(), close_connection(), ]
Agent must manually manage 3 tools for simple query. Error-prone.
Too Coarse-Grained (Bad)
tools = [ do_everything(), # Single monolithic tool ]
Agent has no way to do specific tasks. Inflexible.
Just Right (Good)
tools = [ search_database(query, filters), # Specific, composable fetch_user_profile(user_id), execute_transaction(details), ]
Agent can use tools independently but compose them logically. Perfect.

Tool Error Handling: Critical Pattern

Python: Proper Tool Error Handling
def search_api(query: str, limit: int = 10) -> dict: """ Search external API and return results. Raises: APIConnectionError: API unreachable RateLimitError: Rate limit exceeded InvalidQueryError: Malformed query Returns: {"status": "success", "results": [...]} {"status": "error", "message": "...", "retry_after": 60} """ try: response = requests.get( "https://api.example.com/search", params={"q": query, "limit": limit}, timeout=5 ) if response.status_code == 429: return { "status": "error", "message": "Rate limited", "retry_after": int(response.headers.get("Retry-After", 60)) } return {"status": "success", "results": response.json()} except requests.ConnectionError as e: return { "status": "error", "message": f"API unreachable: {str(e)}", "recoverable": True }

💡 Tool Design Principle: Return Results, Not Errors

Tools should never crash the agent with exceptions. Instead, return structured error responses the LLM can understand and handle. This allows agents to implement their own recovery strategies.

2.3 Memory Architectures in Agents

In-Memory Only (Simple, Ephemeral)

Python: Simple In-Memory Agent Memory
class SimpleAgent: def __init__(self): self.messages = [] # Lost if process crashes! self.context = {} def add_message(self, role, content): self.messages.append({"role": role, "content": content})
Pros: Simple, fast, no DB overhead
Cons: Process crash = memory lost, not shareable across replicas
Use Case: Prototypes, testing, single-turn interactions

Database-Persisted Memory (Reliable, Recoverable)

Python: Database-Backed Agent Memory
class PersistentAgent: def __init__(self, agent_id: str, db: Database): self.agent_id = agent_id self.db = db self.messages = [] # Loaded from DB def load_from_db(self): """Load conversation history from database""" self.messages = self.db.query( "SELECT * FROM agent_messages WHERE agent_id = ?", (self.agent_id,) ) def add_message(self, role: str, content: str): """Add message AND persist to DB immediately""" msg = {"role": role, "content": content, "timestamp": now()} self.messages.append(msg) # Critical: persist immediately, don't wait self.db.insert("agent_messages", msg)
Pros: Survives crashes, recoverable, can scale to multiple replicas
Cons: DB latency, more complex
Use Case: Production agents, long-running tasks

Semantic Memory with Embeddings (Smart Retrieval)

Python: Semantic Memory with Vector Store
class SemanticAgent: def __init__(self, agent_id: str, vector_store: VectorDB): self.agent_id = agent_id self.vector_store = vector_store # Pinecone, Weaviate, Milvus def remember_fact(self, fact: str): """Store fact with semantic embedding""" embedding = embed_text(fact) # Convert to vector self.vector_store.upsert({ "id": f"{self.agent_id}_{timestamp()}", "vector": embedding, "metadata": {"agent_id": self.agent_id, "text": fact} }) def retrieve_relevant_facts(self, query: str, limit: int = 5): """Find facts semantically similar to query""" query_embedding = embed_text(query) results = self.vector_store.query( query_embedding, filter={"agent_id": self.agent_id}, top_k=limit ) return [r["metadata"]["text"] for r in results]
Pros: Intelligent retrieval (not just keyword matching), scales to large knowledge bases
Cons: Embedding cost, vector DB complexity
Use Case: Long-term knowledge accumulation, cross-domain reasoning

⚠️ Memory Pitfall: Context Window Overflow

If your agent has 100 previous messages but Claude's context is only 200K tokens, you can't fit all history. Solutions: (1) Summarize old messages, (2) Only load recent N messages, (3) Embed messages and retrieve semantically relevant ones.

3.2 Detailed Framework Profiles

Claude SDK (Anthropic Official)

🎯 Core Philosophy

Anthropic's official SDK for building Claude agents. Minimal abstractions. You control everything (which means maximum responsibility).

What It Provides:
  • API calls to Claude (text, vision)
  • Tool use definitions and execution
  • Message management (you build memory)
  • Streaming support
What You Must Build:
  • Agent loop logic (Gather → Reason → Act → Reflect)
  • Memory persistence
  • Error handling
  • Tool orchestration
Claude SDK: Minimal Agent Loop
from anthropic import Anthropic client = Anthropic() tools = [ { "name": "search", "description": "Search the web", "input_schema": {...} } ] messages = [] # Phase ①: Gather context user_query = "Research recent AI breakthroughs" # Phase ②: Reason & Decide response = client.messages.create( model="claude-3-5-sonnet-20241022", max_tokens=1024, tools=tools, messages=[{"role": "user", "content": user_query}] ) # Phase ③: Take action if response.stop_reason == "tool_use": tool_call = response.content[1] # Get tool use block tool_result = execute_tool(tool_call.name, tool_call.input) # Phase ④: Observe & Reflect messages.append({"role": "assistant", "content": response.content}) messages.append({"role": "user", "content": tool_result}) # Loop back or exit based on stop_reason

💡 Claude SDK Advantage: Pure Control

You see exactly what's happening at each step. No magical abstractions hiding decisions. This is excellent for learning but requires you to implement everything correctly.

LangChain (Popular Orchestration Library)

🎯 Core Philosophy

"Chains" of components working together. Abstracts common patterns so you write less code. Works with many LLMs (Claude, OpenAI, Gemini, etc.).

What It Provides:
  • ReAct Agent implementation (Reasoning + Acting)
  • Tool integration system
  • Memory management (ConversationBuffer, Summary, Entity)
  • Chain composition (prompt → LLM → output parser → tool)
  • Callbacks for monitoring/logging
What You Build:
  • Tool definitions
  • Agent initialization
  • Custom output parsing if needed
LangChain: ReAct Agent (Much Less Code)
from langchain.agents import Tool, AgentExecutor, create_react_agent from langchain_anthropic import ChatAnthropic from langchain import hub # 1. Define tools tools = [ Tool( name="Search", func=search_api, description="Search the web for information" ) ] # 2. Create agent llm = ChatAnthropic(model="claude-3-5-sonnet-20241022") prompt = hub.pull("hwchase17/react-chat") # ReAct prompt template agent = create_react_agent(llm, tools, prompt) # 3. Run (LangChain handles loop internally!) executor = AgentExecutor.from_agent_and_tools(agent, tools) result = executor.invoke({"input": "Research recent AI breakthroughs"})

⚠️ LangChain Gotcha: "Magic" Abstractions

LangChain handles the loop for you, which is great for speed but bad for understanding. If something goes wrong, you can't easily debug because you don't see each phase. For learning and production debugging, consider Claude SDK first.

LangGraph (State Machine-Based)

🎯 Core Philosophy

Modern approach: agents as state machines. Define nodes (functions), edges (transitions), state structure (what changes). More complex initially but extremely flexible.

When to Use LangGraph:
  • Complex multi-step workflows with conditional logic
  • Multi-agent systems with coordination
  • Agents that need human-in-the-loop decisions
  • Graph-traversal problems (planning, routing)
LangGraph: State Machine Agent
from langgraph.graph import StateGraph from typing import TypedDict, Annotated import operator class AgentState(TypedDict): messages: Annotated[list, operator.add] # Accumulate messages current_tool: str iterations: int def reasoning_node(state): """Decide what tool to call""" return {"current_tool": "search", "iterations": state["iterations"] + 1} def action_node(state): """Execute the tool""" if state["current_tool"] == "search": return {"messages": [{"role": "assistant", "content": "Result"}]} def should_continue(state): """Decide: continue loop or exit?""" if state["iterations"] >= 10: return "end" return "reasoning" # Build graph graph = StateGraph(AgentState) graph.add_node("reasoning", reasoning_node) graph.add_node("action", action_node) graph.add_edge("reasoning", "action") graph.add_conditional_edges("action", should_continue, { "end": "__end__", "reasoning": "reasoning" }) graph.set_entry_point("reasoning") compiled = graph.compile() # Run result = compiled.invoke({"messages": [], "iterations": 0})

💡 LangGraph Advantage: Explicit Control Flow

Every transition is defined. You can visualize the graph, understand exactly what happens when, and handle edge cases explicitly. Perfect for complex production systems.

AutoGen (Microsoft Multi-Agent)

🎯 Core Philosophy

Multiple agents collaborate. Each agent has a role (e.g., "Coder", "Executor", "Reviewer"). Agents send messages to each other autonomously.

Best For:
  • Simulating team dynamics (multiple agents debating)
  • Code generation with human review
  • Complex reasoning (multiple perspectives)
  • Teaching multi-agent concepts
AutoGen: Two-Agent Collaboration
from autogen import AssistantAgent, UserProxyAgent # Agent 1: Coder coder = AssistantAgent( name="Coder", llm_config={"config_list": [{"model": "claude-3-5-sonnet", ...}]} ) # Agent 2: Executor (simulates user) executor = UserProxyAgent( name="Executor", human_input_mode="NEVER", # Auto-execute code code_execution_config={ "work_dir": ".", "use_docker": False } ) # Initiate conversation executor.initiate_chat( coder, message="Write a function to calculate fibonacci" )

3.3 Decision Matrix: Which Framework?

Ask these questions in order:
  • Q1: Do you need multi-agent coordination? → Yes: AutoGen or LangGraph | No: Continue
  • Q2: Do you need complex state management? → Yes: LangGraph | No: Continue
  • Q3: Do you value learning/debugging over speed? → Yes: Claude SDK | No: Continue
  • Q4: Do you want quick prototyping? → Yes: LangChain or Crew AI | No: Claude SDK
