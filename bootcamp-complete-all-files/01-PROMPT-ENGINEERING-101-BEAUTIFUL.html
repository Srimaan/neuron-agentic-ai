Prompt Engineering 101

How to Instruct Claude to Make Good Decisions

⏱️ 90 min lecture + 120 min hands-on 🎯 Beginner 💡 Production-Ready Patterns

🚨 The Problem

Imagine you're building an AI system for a bank that evaluates loan applications. You have Claude API access. Your first instinct:

"Claude, should we approve this loan?"

What happens?

Claude's Response: "I would need to see the applicant's credit score, income, employment status, loan amount, and other factors to make an informed decision. Could you provide more details?"

The problem: Claude doesn't know WHAT to decide or HOW to structure the answer. It's like asking a person to "make a decision" without context, criteria, or format expectations.

This is where prompt engineering comes in.

💡 What is Prompt Engineering?

Simple definition: Writing clear, specific instructions so Claude understands:

  1. What role to play ("You are a loan officer")
  2. What information matters ("Consider credit score, income, employment")
  3. What to decide ("Approve, deny, or escalate to review")
  4. How to structure output ("Format as JSON with decision and reason")
Not magic. It's just being specific and clear. Like explaining a task to a colleague.

📈 The Evolution: From Bad to Good

Let's see how a prompt evolves from bad to good using our loan application example.

❌ Version 1: Vague (This fails)

"Evaluate this loan application. Applicant: John Doe Amount: $50,000 Credit Score: 750 Income: $100,000 Employment: Yes"

Claude's response: "This applicant appears to have good credit and stable income. The $50,000 loan is reasonable given the income level. However, I would need more information..."

What's wrong?

  • No clear decision (approve/deny/review?)
  • No structured format
  • Vague output ("appears to," "would need")
  • No clear rules to follow

✓ Version 2: Better (Getting closer)

You are a loan officer. Decision rules: - Credit score > 700: Good - Income > loan × 5: Can handle payment - Employment: Must be employed

Claude's response: "DECISION: Approved. Reasoning: Credit score of 750 is above 700. Income of $100,000 is 2× the loan..."

What's better? Clear rules, explicit criteria, better reasoning.

What's still missing? No format spec, no edge cases, no JSON.

✅ Version 3: Production-Ready (This works)

You are loan evaluation system. Output format (JSON): { "decision": "approved" | "denied" | "review", "reason": "explanation", "score": 0-100 } Scoring: 80+: Approved 50-79: Review < 50: Denied

Why this works:

  • Clear role specified
  • Explicit format defined
  • Clear scoring rules
  • Machine-readable output
  • Edge cases handled

🎯 The 5 Key Principles

Principle 1: Be Specific

❌ Bad
"Evaluate this loan application."
✅ Good
"You are a loan evaluation system. Output JSON with decision (approved/denied/review)..."

Principle 2: Give Context

❌ Bad
"John Doe, $50k, 750 credit"
✅ Good
"John Doe is applying for $50,000. His credit score is 750 (excellent). Annual income is $100,000."

Principle 3: Show Examples

❌ Bad
"Decide if approved."
✅ Good
// SHOULD APPROVE: Credit: 780, Income: 120k Decision: Approved (score 90+) // SHOULD DENY: Credit: 580, Income: 30k Decision: Denied (score 20)

Principle 4: Specify Format

❌ Bad
"Tell me your thoughts."
✅ Good
Output ONLY valid JSON: { "decision": string, "score": number }

Principle 5: Define Constraints

❌ Bad
"Be objective."
✅ Good
Rules: 1. MUST include numeric score 2. MUST cite which criteria used 3. NEVER approve if employment unverified 4. Do NOT make judgments beyond criteria

⚠️ Common Mistakes to Avoid

Mistake 1: Assuming Claude Knows Context

"Is this a good loan?" — Claude doesn't know YOUR bank's rules. Be explicit.

Mistake 2: Vague Instructions

"Be objective." — What does that mean? Give specific criteria instead.

Mistake 3: Forgetting Examples

"Decide if approved." — Show examples of approved AND denied applications.

Mistake 4: Not Specifying Format

"Give me the result." — JSON? Natural language? Be explicit.
